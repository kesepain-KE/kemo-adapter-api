# 统计读缓存与执行事件落盘边界

统计数据库仍是事实来源。缓存仅用于减少控制台和状态接口的重复 SQL 查询，
不保存待写入的调用记录，也不缓存模型响应、鉴权结果或完整密钥。

## 默认行为

- 日统计、小时统计、排行、时间范围趋势、密钥累计用量、调用日志分页均使用进程内缓存。
- 默认最多 128 项、8 MiB JSON 序列化载荷；这不是整个进程的内存上限。
- 每项固定有效期 30 秒，命中不会延长时间；满容量时淘汰最久未使用项。
- 缓存按完整查询参数隔离，包括日期、时间段、结果类型、分页偏移和数量。
- 新增调用、记录终态、记录重放时清空统计读缓存；下一次读取反映已经提交的数据。
- 空结果也缓存；异常不缓存；返回值单独解码，调用方修改结果不会污染其他请求。
- 同时到达的相同查询只由第一个请求查库，其他请求在锁释放后复用结果。

网关自己写入的数据不需要等待 30 秒才可见。其他进程直接修改或替换统计数据库时，
已有缓存最多保留到剩余 TTL 到期；此机制不承诺多进程缓存同步。
只读查询仍然受原有 API 鉴权保护，浏览器端 `no-store` 策略没有改变。

## 统计写入可靠性

调用开始、终态与用量仍沿用 SQLite 事务写入，不增加定时刷盘队列。
进程退出不会丢失“还在本缓存里等待落盘”的记录，因为此缓存根本不接收写入任务。
统计读缓存不参与 SSE 事件、断线续传或幂等记录；这些能力由独立的 ExecutionStore 管理。
不要把统计读缓存解释为断电或存储设备故障下的零丢失保证。

取消统计请求不会终止已经运行的 SQLite 工作线程：入口等待线程结束再释放锁，
避免后续请求在提交前读到旧数据并将其缓存。失败和取消的写入也清理读缓存。

## SSE 执行事件批量持久化

`core/stores.py` 的 `SQLiteExecutionStore` 使用另一套有界写入缓冲，目的不是缓存查询结果，而是
减少模型流中大量微小事件造成的 SQLite 连接和事务放大：

- 每个 `response_id` 拥有独立 pending 队列，不同请求不共享 Event；
- 默认达到 50 ms、32 条或终态中的任一条件就提交；
- 每条 Kemo Event 仍单独保存 `event_id`、`sequence` 和完整事件 JSON，不改变协议分片；
- 批次提交成功前不会放入可重放 `record.events`，也不会通知 SSE 客户端；
- 终态、取消和关闭会立即 flush，并在同一事务更新最终响应；
- 网关生命周期内复用受锁保护的 SQLite WAL 连接，正常关闭时 checkpoint 并截断 WAL；
- sequence 使用内存中的 `persisted_sequence`，数据库主键和 event ID 唯一约束继续兜底；
- SQLite 提交开始后发生协程取消时，先完成数据库/内存一致性同步，再传播取消。

所以 pending Event 只可能在“尚未提交且尚未向客户端发布”时因进程崩溃而消失。已经发送给客户端
的事件必然先完成本地提交，可以通过 `Last-Event-ID` 精确重放。该设计仍不承诺操作系统、磁盘控制器
或存储硬件故障下的绝对零丢失。

## 维护与验证

统计读缓存实现位于 `storage/read_cache.py`，统计接入位于 `storage/statistics.py`；执行事件缓冲位于
`core/stores.py`，终态组装与写入调用位于 `core/executor.py`。
不要将缓存实例做成跨项目的模块级单例，不要将完整 Provider 配置放进这里。
测试或嵌入式使用可通过 `StatisticsStore` 构造参数调整 TTL、条目数和载荷预算；
任一上限为 0 即关闭缓存，无需给普通部署用户增加环境变量。

```sh
python -m tests --suite storage -q
```

读缓存主要减少重复查询的文件打开、历史库遍历和 SQL 执行，
不会消除持续高并发推理产生的必要写盘。吞吐量和物理磁盘 IOPS 改善需要实机压测衡量。
